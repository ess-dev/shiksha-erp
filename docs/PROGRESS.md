- Plans: landlord tables `platform_modules` (14 sellable modules, snake_case keys), `plans` (price per student per year in **paise**, `min_students`, optional `badge`), `plan_modules`, and `tenants.plan_id` (nullable). `PlanCatalogSeeder` creates missing modules/plans only (never overwrites edited plans; prices illustrative — verify). `UpdatePlan` Action syncs `tenant_modules` for schools whose `plan_id` is that plan (only for the plan-module keys). Screen: `resources/js/pages/platform/plans.tsx`, `components/platform/edit-plan-dialog.tsx`. Not built: subscriptions (trial/renewal/billing), assigning a plan to a school, MRR (card shows "MRR —"), add-on pricing, mapping of plan module keys to the permission catalog's modules (`students`, `leave` are not plan modules).
- Onboarding: `OnboardSchool` (Platform) provisions the database first (`ProvisionTenant::handle(..., audit: false)`, because CREATE DATABASE cannot run in a transaction and the audit rows are append-only), then does everything else in one landlord transaction: tenant details (plan, trial or renewal date, contact incl. new `contact_phone`), `tenant_modules`, identities (reused when the email already exists) + memberships + a set-password link (`IssuePasswordLink`, Identity), the owner (`SetUpSchoolOwner`), other staff (`OnboardStaffMember`, Access: role copied from the template, assigned school-wide, critical permissions confirmed by the platform), and structure (`SetUpInitialStructure`, School: academic year made current, campuses with generated codes and the new nullable `campuses.address` tenant column, optional classes and sections at every campus, run as the owner). Any failure after the database exists calls `ProvisionTenant::discard()`. Single audit event `platform.school_onboarded` carrying the school's tenant_id. Validation lives in `OnboardSchoolRequest`; the wizard keeps its draft in localStorage (`shiksha.platform.onboarding-draft`) and the success page reads the one-time links from the flash session (a reload sends you to School details). Set-password links last `auth.passwords.users.expire` (60 minutes); no email is sent (provider undecided; logging a link would log a token). Choices: web address is suggested from the name and checked against reserved/taken names; the roles offered are the platform role templates except class/subject teacher, plus Teacher (staff record, no role until allocation exists); a paid start renews at the academic-year end and bills nothing (billing is not built); expected students only drives the price estimate; trial length `config('shiksha.trial_days')` (30, illustrative), board and state lists in `config/shiksha.php` (illustrative). Not built: Fees step (Fees module), student import (Students module), sending email, resending an invite, per-school database roles.

## Decisions and conventions worth remembering

- Identities hold sign-in data only (no names). Names live in the tenant `staff` table, linked by `identity_ulid`.
- Membership/identity changes are audited in the **platform** audit table (they write landlord data); school-side Actions audit into the school's `audit_events`.
- Existing Data objects are plain `JsonSerializable` classes; new ones use `spatie/laravel-data` 4.23 (installed 2026-10-22, owner-approved) with `spatie/laravel-typescript-transformer` 3.x. Mark each with `#[TypeScript]` and run `composer types:generate` to refresh the committed `resources/js/types/generated.d.ts` (an architecture test fails if it is stale). Composer platform pin is now `8.3.6` (the 3.x transformer's dependency needs >= 8.3.2). Never send models or internal ids to the browser.
- Scope containment is conservative: a campus scope cannot be shown to contain specific sections (no section-to-campus lookup in `Scope::contains`), so only a school-wide scope may hand out section scopes.
- Template changes need a new version in `AccessCatalogSeeder` (never edit an existing version); schools then see "update available".
- Architecture rule allows only these cross-module uses: other modules' `Actions`, `Queries`, `Data`; `Audit`/`Access` `Enums`; the `Identity` model as the acting principal.

## How to start a new session

1. Read `CLAUDE.md` / `AGENTS.md` (generated from `.ai/guidelines/`) and this file.
2. `git status` and `git log --oneline -10` to see what changed since "Last updated" above.
3. Make sure PostgreSQL is running and `.env` has the local `shiksha` password; `php artisan migrate && php artisan db:seed` brings a local database up to date.
4. Pick the next step above (or the one the owner names), write a short plan, and begin.
